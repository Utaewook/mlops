MLOps 실습 스택 지도

공개 데이터 세 종류(시계열, 이미지, 텍스트)로 학습부터 서빙, 모니터링까지 이어 보는 Docker 실습 환경이다. 어떤 부품으로 되어 있는지, 각 부품이 무슨 일을 하는지, 지금 어디까지 연결됐는지를 그림으로 정리했다.

전체 구조

데이터는 왼쪽에서 오른쪽으로 흐른다. 공개 데이터를 내려받아 시간 순 조각(슬라이스)으로 자르고, 학습 코드가 모델을 만들어 내보낸다. 오른쪽 절반은 모델을 기록하고(MLflow), 서빙하고(Triton), 지켜보는(Prometheus, Grafana) 서비스다. 위에 있는 Dagster는 이 과정을 자동으로 돌리는 역할을 맡는다.

질문 1

이 구조는 많이 쓰는 MLOps 구조인가

부품을 나누는 방식은 표준이고, 도구 조합도 오픈소스로 직접 조립할 때 흔히 고르는 조합이다. 회사 운영 환경과 가장 다른 점은 실행 환경이다. 여기서는 PC 한 대의 Docker Compose로 돌리고, 운영에서는 보통 쿠버네티스나 클라우드 관리형 플랫폼을 쓴다.

Google의 MLOps 문서와 MLOps 아키텍처 연구들이 꼽는 구성 요소는 실험 추적, 모델 레지스트리, 저장소와 메타데이터 DB, 파이프라인 오케스트레이션, 서빙, 모니터링이다. 이 저장소는 요소마다 도구를 하나씩 골라 직접 잇는 조립형이다(노트 10편의 표현). 반대편에는 SageMaker, Vertex AI, Databricks, Kubeflow처럼 한 플랫폼이 여러 요소를 같이 제공하는 통합형이 있다.

도구별 사용 순위를 수치로 보여 주는 최근 설문은 이번에 찾지 못했다. '표준'과 '흔함'은 공식 문서와 아키텍처 연구 정리를 바탕으로 한 판단이다.

성숙도로 보면 지금 위치

노트 2편의 Google 기준(Level 0 수동, Level 1 파이프라인 자동화와 지속 학습, Level 2 파이프라인 CI/CD)에 대 보면, 지금은 Level 0에 인프라만 준비된 상태다. 3·5·6·7편을 마치면 Level 1이 된다.

회사 운영 환경과 다른 점

  • 실행 환경. 운영에서는 쿠버네티스가 단계마다 컨테이너를 따로 띄우고 GPU를 나눠 준다. 여기서는 PC 한 대에서 컨테이너마다 메모리 상한을 걸어 버틴다.
  • 보안. 운영에는 로그인, 권한, 비밀 값 관리 도구가 붙는다. 여기는 127.0.0.1 바인딩과 .env 파일뿐이다.
  • 가용성. 운영에서는 DB와 저장소를 복제하고 백업한다. 여기는 서비스마다 컨테이너 하나다.
  • 데이터 쪽 부품. 데이터 버전 관리(DVC, lakeFS)와 피처 스토어(Feast)는 9편에서 판단 기준까지만 다룬다.
  • 경보와 로그. 경보를 보내는 Alertmanager와 로그 수집 도구(Loki 등)가 없다.

ML 생애주기와 도구의 자리

노트 2편의 Google 8단계에 이 저장소의 부품을 붙였다. Dagster는 앞쪽 여섯 단계를 묶어 자동으로 돌리고, MLflow는 학습부터 검증까지의 결과를 기록한다. 모니터링에서 성능 저하를 잡으면 다시 처음으로 돌아가 재학습한다. 이 되돌아가는 화살표를 자동으로 만드는 것이 MLOps의 핵심이다.

컨테이너 배치와 메모리

서비스는 Compose 프로필로 묶여 있어 필요한 묶음만 골라 띄운다. docker compose --profile serving up -d처럼 쓴다. 컨테이너끼리는 서비스 이름으로 부르고(http://mlflow:5000), 호스트 브라우저에서는 127.0.0.1:포트로 들어간다.

오브젝트 스토리지

모델 파일과 데이터처럼 한 번 쓰고 여러 번 읽는 큰 파일을 HTTP로 주고받는 저장소다. 공유 디스크(NAS) 경로 대신 URL로 파일을 다룬다고 보면 된다. 학습 컨테이너가 사라져도 결과가 남고, 다른 서버가 같은 주소로 받아 간다.

블록 스토리지

디스크를 고정 크기 블록으로 나눠 OS가 직접 마운트한다. 로컬 SSD, AWS EBS.

수정: 블록 단위로 덮어씀

파일 스토리지

디렉터리 트리와 파일. open, seek, write로 중간 수정, 이름 변경, 잠금이 된다. 리눅스 파일시스템, 사내 NAS.

수정: 파일 중간도 가능

오브젝트 스토리지

버킷 안에 키(이름) → 바이트 + 메타데이터. HTTP의 PUT, GET, LIST, DELETE로 다룬다. AWS S3, GCS, SeaweedFS.

수정: 통째로 다시 PUT

S3 API와 'S3 호환'

AWS S3의 HTTP API가 사실상 표준이 됐고, SeaweedFS와 MinIO 같은 제품이 같은 API를 구현한다. boto3나 MLflow는 endpoint_url만 바꾸면 AWS든 로컬이든 같은 코드로 쓴다.

그 밖의 기능: 큰 파일을 조각으로 올리는 멀티파트 업로드, 덮어써도 이전 판을 남기는 버전 관리, 오래된 파일을 지우는 수명 주기 규칙, 정해진 시간만 유효한 presigned URL.

직접 해 본 결과

HEAD 8 bytes
  meta {rows: 2160, source: ETTh1}
같은 키로 다시 PUT
  → GET b'v2-new-bytes'  # 통째로 교체
presigned URL로 GET → 200
그냥 GET → 403         # 자격 증명 없음

맞지 않는 용도도 있다. 작은 값을 자주 고치는 일은 DB가 맞다. MLflow도 실행 기록은 PostgreSQL에, 파일만 S3에 둔다.

MinIO로 바꿔도 되나: 바꿀 수는 있지만 권하지 않는다

둘 다 S3 API라서 compose의 서비스 정의(이미지, 실행 명령, 계정 환경 변수, 포트 9000, healthcheck)와 엔드포인트 주소 네 곳만 바꾸면 된다. create_buckets.py, MLflow 설정, 실습 코드는 그대로다. 문제는 MinIO 커뮤니티판의 상태다.

보안 패치가 더 나오지 않고 이미지가 언제 사라질지 모르는 소프트웨어는 '다른 PC에서 docker와 git만으로 재현'이라는 목표와 맞지 않는다. 노트나 튜토리얼이 MinIO를 쓰는 건 2025년 이전에 쓴 글이라서다. 배우는 개념(버킷, 키, S3 API)은 같다.

Dagster: 파이프라인 지휘자

Dagster는 계산을 직접 하지 않는다. 무엇을 어떤 순서로, 언제, 실패하면 어떻게 실행할지를 관리하고 그 기록을 남긴다. 학습은 우리 mlops 코드가, 파일 저장은 S3가, 모델 버전 관리는 MLflow가 한다. Dagster는 이들을 정해진 순서와 조건으로 불러 준다.

메트릭이란

MLOps에서 '메트릭'은 두 가지 뜻으로 쓰인다. '메트릭 수집'이라고 하면 보통 오른쪽, 시스템이 도는 동안 계속 재는 운영 지표다. 7편의 모델 모니터링은 왼쪽 값을 운영 중에 주기적으로 다시 계산해 오른쪽처럼 시계열로 쌓는 일이라서, 두 뜻이 거기서 만난다.

모델 평가 지표

MAE, 정확도, macro-F1, skill. 학습이나 평가를 할 때 한 번에 한 값이 나온다.

"2017Q2": {"mae": 1.79, "skill": 0.20}

남기는 곳: report.json, MLflow log_metric

운영 지표

요청 수, 응답 지연, 메모리, CPU. 시스템이 도는 동안 계속 변하는 값을 일정 간격으로 잰다.

nv_cpu_memory_used_bytes 2738728960

prometheus_http_request_duration_seconds_sum{handler="/api/v1/query"} 0.003580443
prometheus_http_request_duration_seconds_count{handler="/api/v1/query"} 2

확인해 보니 nv_cpu_memory_used_bytes는 Triton 프로세스가 아니라 WSL VM 전체 사용량이었다. 같은 순간 free -b의 total(8189415424)과 정확히 같다. 이름만 보고 의미를 짐작하지 말고 # HELP와 실제 값을 대조해야 한다. 모델을 올리면 nv_inference_request_success{model="…",version="…"} 같은 모델별 메트릭이 생긴다.

Prometheus: 메트릭을 가져와 쌓는 시계열 DB

Prometheus는 대상의 /metrics를 주기적으로 가져와서(pull) 자체 시계열 DB에 쌓고, PromQL로 질의하게 해 주고, 조건이 맞으면 경보를 만든다. 대상 목록은 infra/prometheus/prometheus.yml에 있다. 지금은 자기 자신과 Triton 두 개를 15초마다 가져온다.

지금 띄운 환경에서 돌린 질의

PromQL결과읽는 법
upprometheus 1 · triton 1대상이 살아 있는지. 수집 실패면 0
sum by (handler) (rate(prometheus_http_requests_total[2m]))/metrics 0.061/s자기 자신을 15초마다 가져가니 1/15 ≈ 0.067
/-/ready 0.18/sdocker healthcheck가 5초마다 확인하니 1/5 = 0.2
nv_cpu_memory_used_bytes2,764,259,328gauge는 값 그대로 읽는다

counter에 rate()를 씌우면 '초당 몇 번'이 되고, 위 결과가 설정한 주기와 그대로 맞는다. 모델을 올리면 이런 질의를 쓴다. 평균 지연(μs)은 rate(nv_inference_request_duration_us[5m]) / rate(nv_inference_request_success[5m]), p95는 histogram_quantile(0.95, sum by (le) (rate(…_bucket[5m])))이다.

가져오는 방식의 약점

짧게 끝나는 배치 작업은 Prometheus가 가져가기 전에 끝나 버린다. 우리 학습 실행이 그렇다. 그래서 학습 결과는 MLflow에 남기고, 꼭 Prometheus에 넣어야 하면 Pushgateway(작업이 값을 밀어 넣어 두는 중간 저장소)를 쓴다.

자체 /metrics가 없는 대상(호스트 OS, PostgreSQL)은 exporter를 옆에 띄워 변환한다. node_exporter, postgres_exporter 같은 것이다. 이 스택에는 아직 없다.

Prometheus가 하지 않는 일

  • 로그와 요청별 추적. 숫자 시계열만 다룬다.
  • 예측값 하나하나 저장. 집계된 수치만 다룬다.
  • 모델 품질 계산. 정답이 나중에 오는 MAE 같은 값은 별도 작업(Evidently, 정기 평가)이 계산해 메트릭으로 내보내야 한다.
  • 장기 보관. 기본 15일이다.

실습 과제 세 종류와 측정 결과

세 과제가 같은 인터페이스(Task)를 따르기 때문에 한 명령으로 돌린다. python -m mlops prepare <과제>로 데이터를 받고, python -m mlops train <과제>로 아래 과정을 한 번에 실행한다.

시계열

ETTh1 변압기 데이터(1시간 간격). 6시간 뒤 오일 온도를 LightGBM으로 예측한다. 모델은 지금 대비 변화량을 맞히고, ONNX 그래프 안에서 현재 온도를 더한다.

기준선 naive는 '지금 값이 6시간 뒤에도 같다'. skill = 1 − MAE ÷ naive MAE.

Vision

EuroSAT RGB 위성 이미지(64×64, 토지 피복 10종). MobileNetV3-Small 전체 미세조정. 미래 구간 t0~t3에 안개를 점점 진하게 입혀 입력 분포 변화를 흉내 낸다.

LLM

KLUE YNAT 뉴스 제목 주제 7종. Qwen3-0.6B-Base에 LoRA(r=8, 학습 파라미터 0.19%). 생성한 답을 라벨로 바꿔 채점한다. 내보내는 것은 어댑터와 토크나이저다.

용어집

아티팩트artifact
실행이 남긴 파일. 모델, 리포트, 그림.
모델 레지스트리registry
모델 버전을 등록하고 별칭(예: champion)으로 어느 버전이 운영 중인지 표시하는 곳.
버킷과 키bucket, key
오브젝트 스토리지의 그릇과 그 안의 이름 문자열. 폴더는 없다.
presigned URL
정해진 시간 동안 오브젝트 하나만 받거나 올리게 허용하는 서명된 주소.
S3 호환
AWS S3의 HTTP API를 같은 방식으로 구현한 저장소. endpoint만 바꾸면 같은 코드로 쓴다.
오케스트레이터
단계를 순서·조건·시간에 맞춰 실행하고 기록을 남기는 도구. Airflow, Dagster.
asset
Dagster에서 만들어 둘 결과물 하나(데이터, 모델). 의존 관계로 그래프를 이룬다.
materialize
asset을 실제로 실행해 최신본을 만드는 것.
partition
asset을 기간 등으로 나눈 조각. 이 저장소의 슬라이스와 대응한다.
sensor와 schedule
조건을 주기적으로 확인해 실행을 요청하는 것과, 정해진 시각에 실행하는 것.
run
파이프라인의 한 번 실행. 로그와 결과가 기록된다.
메트릭metric
이름과 라벨로 식별되는 숫자 시계열.
counter · gauge · histogram
올라가기만 하는 누적값, 오르내리는 현재값, 구간별 누적 개수.
scrape
Prometheus가 대상의 /metrics를 가져가는 일.
exporter
/metrics가 없는 대상 대신 메트릭을 내놓는 작은 프로그램.
PromQL
Prometheus 질의 언어. rate(), sum by, histogram_quantile().
cardinality
라벨 조합의 수 = 시계열의 수. 너무 많으면 저장과 질의가 무거워진다.
드리프트drift
입력 분포나 입력과 정답의 관계가 학습 때와 달라지는 것.
training-serving skew
학습과 서빙의 전처리나 모델이 달라 생기는 차이.
ONNX
프레임워크와 무관한 모델 파일 형식. Triton과 onnxruntime이 읽는다.
LoRA
큰 모델은 고정하고 작은 행렬만 학습하는 미세조정 방법.
Compose 프로필
서비스 묶음에 이름을 붙여 필요한 것만 골라 띄우는 docker compose 기능.
healthcheck
컨테이너가 준비됐는지 주기적으로 확인하는 명령. 다른 서비스가 이것을 기다렸다가 뜬다.
naive 기준선
가장 단순한 예측(지금 값을 그대로 씀). 모델이 이것보다 나아야 의미가 있다.
